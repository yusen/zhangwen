# 双板项目实物仿真与代码部署

## 产品语义

设备实验室不是一张让用户另选开发板的固定演示页。项目立项书确认后，掌问把已确认的
项目硬件、BOM、IO Map 和立项内容投影为一份不可变 `DeviceLabSceneV1`：主控、板载器件、
外接传感器/执行器、连线、来源和待确认项共同组成该项目的实物仿真。

代码部署有两个同级通道：

- USB 串口：部署已接受的 MicroPython CodeRun。
- ESP-Claw：部署已接受的 ESP-Claw Lua CodeRun。

安装或恢复 ESP-Claw 固件属于独立的专业维护操作。它不能替代 CodeRun 部署，日常
ESP-Claw 上传不会调用 `esptool`、整片擦除或 `INSTALL_APPLICATION`。

## 双板范围

唯一可操作的主控 ID 是：

- `dfrobot/dfrobot_k10`（16 MB Flash 档案）
- `seeedstudio/xiao_esp32s3_sense`（8 MB Flash、8 MB OPI PSRAM 档案）

`unihiker-k10`、`unihiker_k10`、`hw_seed_unihiker_k10` 等只在读取历史数据时规范化为同一
K10。外接传感器、执行器、供电和结构器件可以进入项目；第三种 MCU、多主控或无法唯一
确定主控时，场景生成、仿真和部署全部失败关闭。

## V29 场景投影

`device_lab_scenes` 以 `(project_id, revision)` 保存只增不改的场景快照。revision 是规范化
来源、主控、组件、连接和状态的 SHA-256；相同项目事实幂等，立项/BOM/IO 发生变化时创建
新 revision。运行会保存启动时的完整场景快照，因此之后修改立项不会篡改历史运行。

投影顺序如下：

1. 要求存在已批准立项书。
2. 读取已确认 `preferred_hardware`。
3. 若当前立项有已批准 Spec，则合并其 BOM 和 IO Map。
4. 仅在受信本地硬件目录中补充立项正文明确提及的器件。
5. 由精确板级档案补充板载器件和板内连接。

确认 IO Map 产生 `CONFIRMED` 连接；只有立项/BOM、尚无引脚事实的外设产生
`PROPOSAL_DERIVED` 连接，状态为 `NEEDS_IO_CONFIRMATION`。此时 UI 可以显示器件与“待确认
引脚”，但不能把建议线当作真实接线。创建仿真运行只接受 expected scene revision，不接受
UI 传入 `boardId` 覆盖。

## CodeRun 运行时与部署

CodeRun 显式记录运行时和入口文件：历史记录默认 `MICROPYTHON` / `src/main.py`；ESP-Claw
代码使用 `ESP_CLAW_LUA` / `scripts/main.lua`。生成、本地静态结构校验、接受和部署都检查
运行时，避免把 Python 代码通过 ESP-Claw 通道发送或把 Lua 交给 MicroPython 串口上传器。
本地校验覆盖受控路径、危险调用、括号和 Lua block 配平，不冒充完整 Lua parser；表达式级
错误仍由设备运行结果检出，并进入停止任务、恢复文件和失败关闭流程。

统一部署请求使用判别目标：

- `USB_SERIAL` 绑定串口 session。
- `ESP_CLAW` 绑定用户在专业模式中完成受信局域网配对和能力握手的 endpoint。

旧 `/devices/upload` 继续映射 USB 兼容路径；统一 `/devices/deploy` 负责同级通道。两者的
操作类型都是 `UPLOAD_CODE`，共享 operation ID、确认、轮询、取消和审计结果；通道目标、
CodeRun 与来源 Artifact 单独绑定，待恢复请求不能跨通道重试。

首版采用显式 `TRUSTED_LAN_MANUAL` 配对，不宣称已实现 mDNS 自动发现或设备级认证。用户须在
专业模式分别填写同一台设备的 Web Console origin 与 MCP endpoint，并确认受信局域网、设备
Admin Mode 和精确板型。只接受私网 IP 或 `.local` 的明文 HTTP，禁止 URL 凭据、查询、片段、
跨主机端点和不安全路径；这是对上游局域网控制面的受限兼容，并不把“可访问”冒充“已认证”。
普通模式只显示已在专业模式配对、与当前项目板型一致且状态为 READY 的脱敏目标，不挂载地址
输入或信任确认表单。

真实写入前仍须满足：端点已配对、只读能力握手完成、精确板型匹配（或由用户明确确认）、
运行时为 ESP-Claw Lua，并具备文件回读、异步运行和 job 查询能力。部署使用版本化脚本路径，
写入后读回 SHA-256，再执行 Lua 异步任务并确认完成或稳定运行；任一门禁失败时零写入。当前
自动测试只使用受控 Fake adapter，不连接局域网设备。后续可在不放宽这些门禁的前提下增加
mDNS 候选发现。

managed job name 只按项目稳定生成，因此同一设备通过 IP 或 `.local` 别名重新配对仍会替换
同一任务。取消、超时、运行失败和正常退出必须先确认远端任务进入明确终态，再恢复文件；
未知状态或服务重启后的孤儿 operation 不能显示“已取消”。恢复旧文件需要逐字节回读，删除
本次新建文件需要回读为不存在，之后才能记录恢复成功。任何一步无法确认都令会话进入 ERROR，
并要求用户先人工停止执行器和检查设备。

## 应用初始化与恢复

专业模式保留预构建 `.zwapp.zip` 的导入与运行时安装，用于首次初始化或故障恢复。不在用户
电脑编译 ESP-IDF/ESP-Claw。manifest 校验精确板型、ESP32-S3、Flash/PSRAM、镜像路径、
SHA-256、段边界/重叠和受保护分区。

安装仍需独立确认，按段备份、写入、回读与失败恢复；不执行整片擦除，不覆盖 NVS/用户数据。
Flash、终端、USB 上传、ESP-Claw 部署和参数同步按物理目标互斥。

## 仿真与 Wokwi Elements

`@wokwi/elements` 由桌面前端本地打包，只负责器件外观和交互控件。实际状态由项目场景、
本地功能模型或受控 ESP32-S3 QEMU 计算。K10 与 XIAO 的板级功能档案是基线，项目选定的
外围器件和连接在其外层动态生成；XIAO 开启 SD 时锁定 GPIO21 LED。

每个场景同时生成绑定 scene revision 的 `DeviceLabProfileV1`。板载通道沿用精确板级档案；
立项中的外接传感器自动获得明确标注的 0–100 功能夹具输入，外接执行器/显示获得需解锁、
断线归零且受可保存输出上限约束的功能夹具。这里不编造真实单位、电气量程或总线时序；
只有具备更精确器件档案时才应替换通用夹具。

`QemuRuntimeManager` 只启动固定版本与 Hash 的可选本地组件。当前仓库未包含 QEMU 二进制，
所以 API 如实返回不可用并使用功能模型；这不等同于已交付固件级 QEMU。摄像头图片/视频、
麦克风波形/WAV、虚拟 FAT32 和音频捕获都是功能夹具，不代表模拟电气、射频或周期精度。

## 图形化调参与安全

传感器仿真值可由滑块、数值、开关、波形或媒体夹具输入；真机原始读数只读。执行器必须
显式解锁，并受档案范围、刷新率、安全值、停止和断线看门狗约束。参数先保存为不可变项目
版本，再由用户明确“应用到仿真”或“同步到设备”。参数板型必须与当前项目场景一致。

真机参数同步使用 staging、读回 Hash、原子提交和失败恢复。实时真机图形调试仍要求固件
完成版本化调试协议握手；没有协议的任意固件不会获得虚假调参能力。Wi-Fi 密码和令牌不
持久化；配对端点只保存在本机设备注册表，不进入项目导出、参数版本、代码、日志或测试
夹具。项目包隐私扫描还会阻止私网/`.local` HTTP(S) 地址及 ESP-Claw 本机会话标识外泄。
