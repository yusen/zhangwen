## 2026-07-30 双板项目实物仿真例外

“项目实物仿真”是用户明确授权的中央工作区，只能面向 `dfrobot/dfrobot_k10` 与
`seeedstudio/xiao_esp32s3_sense`。进入实验室时，既有 `CenterChat` 必须保持同一
React 实例挂载，仅使用可见性切换隐藏；返回对话后消息、草稿、附件、引用和滚动位置不得丢失。

- 右侧一级 Tab 仍固定为“工作 / 产物 / 设备”，设备实验室不是第四个右侧 Tab。
- 场景必须来自已批准立项，不提供主控板选择器；显示项目主控、外设、接线来源和待确认 IO。
- 设备页的代码部署区同级显示“USB 串口 / ESP-Claw”，两者共用已接受代码、确认、进度、取消和结果；ESP-Claw 不得藏在固件应用安装卡中。
- ESP-Claw 运行时初始化/恢复只在专业维护区出现，并明确说明其独立于日常代码上传。
- ESP-Claw 双地址、可信 LAN/Admin/精确板型确认和“手动配对”表单只在专业模式挂载；普通
  模式只列出同项目板型、READY 且地址脱敏的既有目标，ERROR 或错板目标不得自动选中。
- 普通模式只显示项目场景、代码通道和用户可理解的能力限制；来源 Hash、协议、job 和运行时维护细节留给专业模式。
- Wokwi Elements 只承担板卡/元件外观与交互控件，所有状态计算由本地受控引擎完成；界面不得把组件显示称为电气或时序精确仿真。
- 真机传感器原始读数只读；执行器必须先解锁，显示中文范围/刷新率状态，并持续提供停止入口。断连、停止和重连均保持安全值。
- 参数先保存成不可变项目版本，再由用户明确选择“应用到仿真”或“同步到设备”；两种动作不能合并成自动写入。
- 390、720、1280 宽度下不得出现页面级横向溢出，中央实验室内部区域可以在自身容器内滚动。

## V2 覆盖声明（2026-07-26）

`docs/PRD_V2.md` 和 `ZW-V2-001` 覆盖本文件下方保留的 V1 布局规则。V2 当前生效契约如下：

### 2026-07-28 ZW-UX-009 M7 对话流体化修订

本节覆盖下方 M6 中普通模式的澄清、导航、状态和结果卡表达；专业模式与既有安全门禁继续有效。

1. 普通模式以中央对话为首页。左侧只显示“对话 / 项目 / 连接 / 设置”，右侧检查器默认真正隐藏；窗口进入 `<=860px` 时自动收起已打开的检查器，用户仍可按需以抽屉方式重新打开。概览、工程、结构、交付只在专业模式显示。
2. 普通模式不得出现“需求澄清、完整度、第几题、上一题、下一题、提交回答”等问卷语言。每次只把一个真正阻塞的问题显示为普通掌问消息，用户直接在主输入框回答。
3. 当前问题只保留“按掌问建议继续”和“我自己说”两个可选捷径。历史多问题 payload 必须在前端逐个自然呈现，全部收齐后仍通过既有 `clarification_batch_answer` 一次提交，不改变后端完整回答事务。
4. 普通模式生成过程只显示一个当前状态，不显示步骤清单、Agent、Worker、Job、路由或自动恢复轮次；只有恢复达到上限时才用自然语言说明原因与下一步。
5. 普通模式的方案、代码和 3D 卡只显示标题、最多两行摘要和一个主要动作，例如“查看代码 / 查看 3D / 连接设备”。专业模式保留版本、文件、语言、来源、诊断和完整状态。
6. 查看代码、3D、成果或设备时只能展开既有右栏或浮窗；`CenterChat` 不得卸载，草稿、滚动、附件和引用必须保留。
7. 可逆、低风险细节由系统采用推荐默认值并继续；非阻塞缺口记为验证项；改变产品方向时最多询问一个最高影响问题。串口扫描、连接、上传、复位、Flash 和固件烧录继续保留明确确认，不得自动执行。

### 2026-07-28 ZW-UX-009 M6 简洁交互修订

ZW-UX-009 保留“对话即工作台”的 Studio 壳，并在 M6 按真人体验收敛信息层级。本节覆盖
下方第 2、3、4、8、15 条中的布局描述；未被提及的行为契约（数据真实来源、确认点、能力
门禁、回退等）继续有效。

1. 壳结构固定为：深色图标轨（主导航）｜中央舞台｜右侧上下文检查器｜底部状态栏。项目与版本导航改为图标轨触发的左侧滑出面板，不再常驻左列。
2. 中央舞台默认显示对话；概览/工程/结构/交付只通过左侧图标轨切换，顶部不得再复制第二套同级页签。`CenterChat` 在工作台生命周期内仍只挂载一次，切换只隐藏不卸载，历史、草稿与滚动状态不丢失；对话保留最后访问工作区的上下文。
3. 右侧一级 Tab 固定为“工作 / 产物 / 设备”。“工作”合并当前内容、待确认修改、已确认信息和正在处理事项；内部 Change Set、Fact 与 Job 只在专业模式解释。“设备”首次点击才挂载既有 `DevicesTab`，访问后切换 Tab 或折叠侧栏只隐藏，不销毁连接摘要和操作上下文。
4. 状态栏普通模式只显示本地服务状态与“暂无后台任务 / 正在处理 N 项”；云端 Provider 和“本地任务”等工程名称只在专业模式显示。
5. V2 设计 token 唯一事实源为 `apps/desktop/src/styles/v2-tokens.css`（`--zw-*`）；浮窗与共享对话框仅经 `.zw-shell` 作用域覆盖统一外观，V1 壳与 `App.css`/`visual-system.css` 不变，`VITE_ZHANGWEN_V2_UI=0` 回退继续有效。
6. 普通模式不得显示 Change Set、CAD Intent、Worker、Job、Artifact、Project Version、Release、hash、原始状态码或操作路径；改用“待确认修改、3D 方案、正在处理、项目成果、保存记录”等任务语言。专业模式保留精确工程信息。

1. 登录门禁继续生效；认证前不挂载项目 Hook、工程工作区或 AI 协作面板。
2. 一级工作区固定为“概览 / 工程 / 结构 / 交付”。中央区域展示实际工程页面，不再永久锁定为对话。
3. 同一项目只有一个 AI 协作面板、一个聚合时间线和一个项目草稿。`CenterChat` 在 V2 工作台生命周期内只挂载一次；切换工作区、工程二级视图、版本、Change Set、Job 抽屉、普通/专业模式时只隐藏或改变上下文，不卸载。
4. 项目与版本导航位于左侧滑出面板；右侧“工作 / 产物 / 设备”可折叠；生成、上传和恢复进度并入“工作”，设备操作只在“设备”执行。
5. 工作区、对话、Change Set 和 Job 的所有状态都有中文文字标签，不能只依赖颜色。
6. 前台只突出一套当前推荐方案；候选变化进入 Change Set，并明确显示操作、影响、风险、确认和提交状态。
7. 普通模式隐藏内部 ID、源码哈希、能力来源、Worker Trace、串口标识和高级参数；专业模式才展开。
8. 窄屏时项目导航、AI 协作和 Job 分别变成互斥抽屉；工作区仍可访问，不产生页面级横向滚动。
9. V1 `AppShell` 通过 `VITE_ZHANGWEN_V2_UI=0` 保留为迁移回退；生产构建默认进入 V2，自动测试可直接验证两套 Shell。
10. 云端 LLM 仍不直接执行文件、Shell、串口或 CAD；工程页面只能创建 Change Set/Tool Job，由受控本地主机执行。
11. 已有 V1 项目进入 V2 时必须显示“V1 导入基线”而不是误报 V0；空白新项目才显示 V0。该基线没有 Change Set，不得伪造成用户提交。
12. 工程二级页必须消费实际项目数据：硬件显示 confirmed `preferred_hardware`，代码显示真实 CODE Artifact 与当前版本预览，设备复用受能力门禁和确认点保护的 `DevicesTab`，验证读取 `ProjectProgressSnapshot`。没有对应记录时应明确显示空态，不得把 AI 对话中的文字当成已经实现。
13. 交付页同时列出 V2 Project Version/Release 与既有 Artifact；从 V1 导入的文档、代码和模型仍可查看，不能因 `project_versions` 过去为空而消失。
14. “已确认事实”默认只显示可读中文标签与摘要。澄清事实必须沿来源消息恢复原问题和所选选项；硬件只显示名称与校验结论。`q_*`、component ID、revision 和原始 JSON 不得占据普通内容区；专业模式可以小字显示事实 key，但仍不得用单行 JSON 撑破布局。
15. 右侧“工作”必须用普通任务语言显示当前页面用途。概览默认由问题引导师负责，工程各子页默认由智能工程师负责，结构由结构工程师负责，交付由智能工程师核对；专业模式允许用户在当前页覆盖主责工程师。切页只改变上下文和路由，不重挂 `CenterChat`，不得丢失历史、草稿或滚动状态。
16. 对话请求可携带受限的 `workspaceKind/workspaceView/projectVersion` 导航提示。Sidecar 必须使用固定 allowlist 重新验证，并明确该提示不授予 CAD、文件、Shell、串口、上传或设备权限，也不证明工具已经执行。

## 不可变约束

1. 未认证时只显示注册/登录门禁，不挂载 `AppShell`、项目 Hook 或 `CenterChat`；认证成功后中央区域始终为主对话，不因查看任何产物而路由到其他页面。
2. `CenterChat`（MainConversation）在项目工作区生命周期内只挂载一次。
3. 切换右侧 Tab、折叠任一侧栏、切换普通/专业模式，以及打开设置、项目创建、项目工具或浮窗时，不得卸载 `CenterChat`。
4. 输入草稿、滚动位置、附件和引用上下文不得因上述界面变化而丢失。
5. 右侧一级 Tab 固定为“工作 / 产物 / 设备”，不得新增普通用户可见一级 Tab。
6. 所有状态必须同时显示中文文本，不能仅依赖颜色。
7. 前台一次只突出一套当前推荐实现方案；旧版本保留在产物历史中。
8. 普通模式隐藏 Agent、Skill、工具链、内部 ID、高级设备信息，以及服务商、Base URL、精确模型、思考模式和请求超时等高级模型参数；设置中只显示供应商无关的模型服务摘要、安全凭据状态/入口和连接状态。专业模式入口只放在设置中。
9. 左栏保留完整“新建项目”入口，顶栏提供带无障碍名称的快捷按钮；两者打开同一创建覆盖层。创建表单、重命名、软删除/恢复、项目包和硬件库不得替换中央对话。
10. 云端 LLM 不直接执行文件、Shell 或串口操作；设备控制只能进入本地受控流程。
11. 一个项目在用户界面上只有一条时间线和一个项目级输入草稿；智能体不再拥有可见的独立聊天窗口。
12. 项目参与智能体以输入框上方的胶囊展示；点击胶囊或输入 `@智能体` 只改变下一条消息的路由目标，不切换中央窗口。
13. 新建项目的模型推荐只能由用户点击“分析并推荐”触发；输入变化本身不得发起网络请求，修改已分析创意必须使旧推荐失效。
14. 当前项目未加入全部三师时，工程师胶囊末尾显示“＋ 添加工程师”；添加只创建或恢复该项目的独立线程，不复制聊天。
15. 普通生成失败不能把对话停在一行错误文字。失败消息必须显示中文原因、解决建议和至少一个明确动作；
    恢复仍在同一 `CenterChat`、同一项目和原专家线程完成，不得打开第二套聊天界面。
16. Windows 原生标题栏/任务栏、桌面 EXE/安装器、favicon、登录页和常规宽度顶栏使用同一掌问品牌 Logo；
    `<=520px` 页面顶栏可隐藏重复品牌元素以保持项目切换、健康状态和操作按钮可达，但不得因此改变中央主对话或
    右侧固定三 Tab。

## 区域职责

- 顶栏：产品名、新建项目快捷入口、项目切换、当前阶段、本地服务健康状态、项目工具和设置。本地服务健康状态仅表示本地 API 可达，使用“本地服务正常 / 本地服务未连接”，不得解释为 LLM 或硬件已连接。
- 左栏：新建项目、项目列表和当前项目资源。
- 中央：一条按时间排序的项目消息历史、回复智能体名称、整组澄清卡、智能体胶囊和项目级固定输入区。
- 工作：按“当前事项 → 紧凑任务摘要 → 固定五项 MVP 交付就绪度”展示真实项目状态；就绪度只包含总分、细进度条和需求/方案/代码/CAD/教案五行，不呈现工程流水线、工作计划或各产物分段。确认仍只在中央主对话完成。Agent、Skill、模型路由、宿主能力等内部工程详情只在专业模式按需加载。
- 产物：普通模式优先突出唯一当前方案，并提供类型/状态筛选；专家筛选、来源、依赖和详细版本信息只在专业模式显示；复杂预览进入浮窗。
- 设备：普通模式按“代码准备 / 连接设备 / 确认上传 / 查看结果”显示连接摘要与当前可执行动作；日志、VID/PID、序列号、固件和 Dry Run 等高级信息只在专业模式显示。硬件连接状态仅在右侧“设备”展示，不复用顶栏本地服务状态。
- 右栏 Tab 首次访问时才挂载对应内容，避免未打开设备页就触发扫描；访问后切换 Tab 或折叠右栏只隐藏面板，不销毁筛选、连接摘要或操作上下文。Tab 始终同时保留图标和“工作 / 产物 / 设备”中文文本。

## 设置与模型服务信息分层

- 普通模式只显示供应商无关的云端 LLM 服务摘要、安全凭据状态/入口、连接状态和连接检查动作；凭据不得明文回显，仍遵守既有主机能力与安全存储边界。产品界面不区分免费或付费模型模式，也不展示 `standard`、`fake`、`paid` 等内部开发配置；LLM 连通性仅由设置中的连接检查结果表达，未执行检查时不得宣称已连接。
- 服务商、Base URL、精确模型、思考模式和请求超时仅在专业模式显示。
- 专业模式的 Base URL、精确模型、思考模式和请求超时放入默认折叠的“高级连接参数”；打开设置首屏仍以服务状态、凭据和主要动作优先。
- 自定义模型入口仅位于专业模式默认折叠的“高级连接参数”中。添加项只接受受控模型 ID，保存前在当前 Provider 下显示“自定义”标识并可移除；普通模式不得请求用户填写、显示或管理自定义模型目录。该入口使用紧凑表单和列表，不新增设置一级页、右侧 Tab 或第二套模型状态。
- 开发态 Tauri 即使携带 Vite 本地 Origin，只要桌面 capability 有效，仍可保存、携 Key 测试和清除凭据；普通 Web 与伪造/缺失 capability 不得获得凭据能力。
- 保存失败必须展示服务端给出的可行动原因并保留尚未保存的 API Key。连接测试若使用了与持久配置不同的当前表单，成功文案必须明确“请先保存设置，之后对话才会使用该配置”，不得宣称对话已经切换。
- 设置沿用现有 `AppShell` 覆盖层和真实配置/API 状态，不引入原型假模型或平行状态；打开、关闭或切换设置模式不得卸载 `CenterChat`、改变项目草稿或新增“工作 / 产物 / 设备”之外的一级 Tab。

## 尺寸

- 左侧栏宽度：240px（可折叠）
- 右侧栏宽度：320px
- 顶栏高度：48px
- 右栏折叠宽度：36px

响应式规则：

- `721-1000px`：左栏缩为 220px，右栏缩为 300px，中央对话继续占剩余空间。

## 生成失败恢复

- 智能工程师出现 `LOCAL_OUTPUT_REJECTED` 时，不显示需要点击的恢复按钮；原失败位置只显示“本次生成未通过本地校验，正在/已按原需求自动重试”，随后自动复用原需求、原专家和原会话创建恢复轮次。连续恢复仍失败时继续自动重试，每条失败链最多自动恢复三次。达到上限后停止自动请求并显示包含原因、上限和下一步的中文终态，不恢复“按原需求重试”确认按钮，也不得无限循环。
- 其他专家的 `LOCAL_OUTPUT_REJECTED` 显示“生成结果未通过本地校验”，只概括当前工程上下文、代码、凭据、主机文件访问或设备安全边界；不得把尺寸冲突、孔位或器件资料缺失列为要求用户修改需求的原因，必须明确原需求本身不需要修改，并只提供“按原需求重试”。当前硬件机械尺寸、孔位或器件资料不完整不得让智能工程师整轮失败，应作为后续工程验证事项保留。
- `LLM_OUTPUT_INVALID` 显示“云端结构化输出不完整”，说明通常不是用户需求本身错误，并提供“重新生成 / 检查模型设置”。
- `GENERATION_INTERRUPTED` 以及历史“上次生成被中断”显示“生成过程已中断”，说明可能来自应用关闭、Sidecar 重启或连接断开，并提供“继续生成 / 修改原需求”。
- 中断恢复中的“修改原需求”把失败轮次的原始用户文本恢复到项目输入框并聚焦，不自动发送；“重新/继续生成”创建新恢复轮次，沿用原专家和对话，原失败卡保留。本地安全拒绝不提供“修改原需求”。
- 恢复轮次在聚合时间线显示简短状态事件，不重复渲染整段原需求。按钮执行期间禁用，原消息无法定位时必须保留文字解决建议，用户仍可从固定输入框继续。

## 浮窗

统一接口：

```ts
interface FloatingWindowSpec {
  id: string;
  kind: 'document' | 'code' | 'model3d' | 'image' | 'terminal' | 'web-preview' | 'hardware-component' | 'hardware-skill' | 'agent-package';
  title: string;
  artifactId?: string;
  versionId?: string;
  initialBounds?: { x: number; y: number; width: number; height: number };
  singletonKey?: string;
}
```

同一 `singletonKey` 只能打开一个实例。最多 3 个浮窗。

浮窗层必须高于左右侧栏覆盖层。`<=720px` 从产物、设置或项目工具打开浮窗时自动收起右栏，避免右栏遮挡浮窗内容；该动作不得卸载中央对话或清除草稿。

### MicroPython 代码产物浮窗

- Code Artifact 继续从右侧“产物”打开浮窗；“代码 / 变更”是浮窗内固定二级视图，不新增右侧一级 Tab，也不改变中央对话路由。验证不是独立页签。
- Python/Markdown 编辑使用本地 `monaco-editor` ESM API 和本地 Worker，不从 CDN 加载。浮窗父组件持有文件草稿，Monaco 只提交文本变更，因此切换文件或视图不会重建版本状态。
- “代码”视图提供已有文件切换、逐文件文本编辑、变更摘要、放弃修改和“保存新版本”。切换文件或二级视图不得丢失当前浮窗内草稿。
- 编辑区必须持续显示：“未保存修改智能工程师不可见；保存后下一次回复可见”。只有内容实际变化且摘要非空时允许保存。
- 保存成功后浮窗切换到新 CodeRun/ArtifactVersion；旧版本仍可从产物历史读取。保存后的用户版本明确显示待验证，不得显示为已接受或可上传。
- 保存返回 409 `CODE_REVISION_CONFLICT` 时，当前文件草稿和变更摘要必须原样保留，并用文字提示用户基于最新版本重新应用修改；不得自动刷新覆盖用户输入。
- “变更”视图显示版本、来源、变更摘要和 unified diff。代码视图底部紧凑显示静态与语法两项检查状态，并可展开命令、输出和真实退出码；有未保存修改时禁用最终验证。
- 验证状态只由 `exitCode` 渲染：`0` 为“通过”，非零为“失败（退出码 N）”，`null` 为“未运行”。不得因输出文本含有 `PASS` 或 contract 中的 status 字段而覆盖退出码结论。
- 历史智能工程师消息导入时，代码产物只显示消息中实际提供且会上传的安全 `src/*.py` 文件；不得补出 README、测试或未被消息提供的配置/驱动占位文件。旧导入版本继续作为不可变历史保留。
- 代码视图只提供一个“验证并接受代码”主动作：先重新运行静态与语法检查，只有两项真实退出码都为 `0` 且状态为 `READY_FOR_REVIEW` 时才调用接受接口。接受期间禁用重复操作；成功后显示“代码已接受”，刷新产物和设备页的当前代码，但不重新扫描串口或覆盖浮窗草稿。失败只保留结果供修改，不得接受或上传。
- 打开、保存、验证或关闭浮窗时，页面仍只有一个 `main`/`CenterChat` 实例，中央草稿、右侧“工作 / 产物 / 设备”及当前推荐方案保持不变。
- “代码”视图必须以 Monaco 为主体：版本元数据压缩到浮窗标题或紧凑工具条，文件标签位于编辑器上方，变更摘要与保存操作位于编辑器下方；在 720px 及以上视口，编辑器应占代码视图大部分可用高度，不得被大块说明或元数据挤到首屏之外。
- 新版本本地检查只显示“静态检查 / 语法检查”两项，不再显示或执行模拟验证。历史版本中的 `SIMULATION` 记录可以保留在数据中，但不作为当前接受门禁或默认界面内容。

## 中央确认流

- 中央“待你确认”卡只承载会推进明确领域状态或本地副作用授权的操作：执行计划审批、CAD、教案，以及本地 Skill Runtime 生成的明确执行授权。问题引导师流程暂不展示 Spec 确认卡；代码验证与接受只在代码浮窗完成，不再出现中央代码确认卡。

- 确认卡一次只显示一个真实可执行事项；确认或退回后刷新当前项目。卡片必须显示事项类型、标题、必要说明和清晰的确认/退回命令，不得只用颜色表达状态。
- 右侧“工作”只显示当前进度、任务摘要、产物状态与非确认型操作，不得继续放置“确认继续”“确认 Spec”“接受代码”“确认 CAD”“确认教案”“确认或处理”等用户确认入口。

- 中央确认卡出现、操作和刷新期间，`CenterChat` 保持单一挂载，未发送草稿、滚动位置、附件和引用不丢失。

## 项目交互可靠性

- 每次流式生成固定绑定不可变的 `projectId + conversationId + requestId`。流开始后切换专家只改变下一条消息路由，已在进行的事件仍写回原项目、原会话和原助手占位；不属于当前请求作用域的迟到事件必须忽略。
- 生成中切换项目或退出时，先终止当前请求、调用服务端取消并等待本地流读取收敛，再刷新项目草稿和改变工作区。界面不得只显示“将停止生成”却让旧请求继续运行或把迟到事件写入新项目。
- 项目输入草稿持续显示“未保存 / 保存中 / 已保存 / 保存失败”四态，失败必须提供重试。切换项目、新建项目或退出前必须刷新当前草稿；失败时保持当前工作区，只有用户明确确认放弃未保存内容后才能继续。
- 中央确认卡与右侧“工作”消费同一个项目工程状态快照，计划、Spec、代码、CAD 和教案不得各自重复请求形成短暂分歧。部分读取失败必须显示可重试错误并保留最后一次有效快照；不得把失败静默解释成“没有待确认事项”。

## 中央对话消息与澄清

- 每条助手回复显示稳定的 32px 专家语义头像、中文专家名和内容气泡；问题引导师、智能工程师、结构工程师分别使用现有 guide/engineer/structure token。头像只作识别辅助，不能替代名称。
- 助手正文气泡按内容自适应并限制最大宽度，不得横向铺满中央工作区；方案和产物卡与正文位于同一消息主体。当前待答整组澄清从来源消息中投影到中央输入区上方的单一吸底浮层，不创建第二条对话、页面或独立状态模型。
- 流式请求尚未收到 `chat.progress` 时显示“{专家名}正在生成回复”和三个动态圆点，作为旧服务端和无进度路径的回退；收到真实动作后切换为动作进度，失败、取消或请求结束后不得继续动画。`prefers-reduced-motion` 下关闭位移动画。
- 普通模式不得展示 `reasoningContent`，不得从模型正文、思考内容、等待时长或客户端猜测“读取知识库”“执行工具”“操作硬件”等动作；所有可见动作必须来自当前请求的 `chat.progress / PROGRESS` 事件。
- 需要用户补充需求、参数或偏好时，ExpertRuntime 必须返回 `uiPayload.type=clarification` 的 1-6 个结构化问题；`content` 只作简短引导，不得用纯文本问题或模型生成的 `MISSING_INPUT`/`CONFIRMATION` PendingItem 收集答案。
- 整组澄清卡显示“需求澄清”类型、`已完成 N/M`、当前“第 K/M 题”、文本进度和进度条；一次只吸底显示最新待答组，并位于消息滚动区之外、草稿状态与输入区之上。卡内一次只呈现一问，通过“上一题 / 下一题”逐题选择；当前必答题完成后才允许下一题，多选题不自动跳转，最后一题才显示整批提交。1-6 题时卡片自身限制高度并内部滚动，不能遮住输入区或造成页面级横向溢出。选择项、自定义输入与一次性批量提交继续使用原有 question/source message/client turn 事务，不得在前端从 PendingItem 文本猜测问题。
- 澄清提交进行中吸底卡保持原位并禁用，成功后收起；取消、网络失败或停止生成必须恢复同一来源消息的原选择草稿并重新启用。切换项目只显示目标项目自己的待答组，且不得重挂载 `CenterChat`。
- 问题引导师确认当前实施基线后不再生成或显示待确认 Spec，也不要求用户再次输入“继续”或复述基线。项目中已有智能工程师时，桌面自动切换到该专家并基于已确认立项书开始执行；没有智能工程师时只保留已确认基线，不静默新增专家。底层 Spec API 和历史数据只作兼容，不进入该前台链路。
- 问题引导师方案卡必须同时提供“生成立项书”和“生成教案版本”两个明确出口。两者都在同一次动作中确认当前方案并生成表格式实施基线；教案路线把选择持久化到项目共享上下文，后续 Spec 确认只生成教案，不同时生成代码。历史“确认方案”动作继续兼容为工程立项路线。
- 中央方案卡只显示标题、版本、状态、单段摘要和紧凑操作；完整章节、修订前后对比和依赖信息统一在既有 Artifact 浮窗中查看。点击“查看完整方案 / 打开浮窗”不得在中央内联展开第二份全文，也不得替换或卸载 `CenterChat`。

## 真实动作进度

- 动作进度放在当前专家回复气泡内，显示一个当前动作和紧凑的已完成步骤；沿用同一头像、专家名和消息主体，不创建第二条时间线、独立执行面板或新的右侧一级 Tab。
- 普通模式只显示 Sidecar 白名单提供的中文 `label` 与“进行中 / 已完成 / 等待 / 受阻”语义。`action`、`id`、`sequence` 只用于客户端排序和去重，不得显示；Skill/Tool 名称或 ID、命令、路径、端口、payload、内部请求 ID、原始错误、模型推理和真实硬件标识均不得出现。
- `RUNNING` 表示 Sidecar 已进入真实阶段；`COMPLETED` 表示该阶段已完成；`WAITING` 表示仍有本地授权或前置条件，不能画成正在执行；`FAILED` 只显示清洗后的白名单文案。只有 ToolRunner 已持久化真实 `RUNNING` 记录后，才能显示“正在执行本地工具”；`AWAITING_CONFIRMATION` 只能显示“等待本地执行授权”。
- 当前动作使用 `role=status`、`aria-live=polite`，状态变化不能只依赖颜色。终止、失败或取消必须停止运行态动画；`prefers-reduced-motion` 下保留文字与状态图标但关闭位移动画。
- 进度属于当前请求的瞬态 UI 状态，不写入历史消息正文或 v25 授权关联；项目重开或历史回放不得伪造或恢复已结束动作。成功、失败、取消和用户停止都必须恢复原消息终态、清理动作并刷新授权事项，不能改写原回复正文或重挂载 `CenterChat`。旧服务端完全没有 `PROGRESS` 时保留三点生成状态，不得把缺少事件解释为失败。
- CadJob/CAD Worker 和设备上传、连接、重启等异步流程继续在右侧“工作 / 设备”及既有浮窗中显示各自持久状态；它们不得作为本轮专家回复的聊天动作重复呈现。无论进度出现或消失，`CenterChat` 保持单一挂载，草稿、滚动位置、附件和引用不丢失，右侧一级 Tab 仍固定为“工作 / 产物 / 设备”。
