# 掌问 Qoder × Codex 协作开发方案 v1.0

**文档状态：** 可执行基线  
**适用项目：** 掌问——AI 创客工程工作台  
**适用阶段：** ZW-003 收尾及后续所有阶段  
**主要开发者：** 单人开发  
**工具约束：** Qoder 作为日常主开发工具；Codex Plus 受使用窗口限制，仅用于高风险、高复杂度和关键集成任务  
**更新时间：** 2026-07-08

---

## 1. 文档目的

本方案用于统一“掌问”项目后续开发中的任务规划、用户确认、工具分工、代码交接、最小测试、阶段验收和 Git 管理方式。

本方案解决以下问题：

1. 避免每次给 Qoder 编写很长且重复的提示词；
2. 避免 Qoder 与 Codex 对同一功能重复实现、重复验证；
3. 在 Codex 有使用额度限制的情况下，将其集中用于最高价值工作；
4. 确保关键产品规则不会因为切换工具而丢失；
5. 使所有开发状态落在仓库文件和 Git 中，而不是依赖聊天记录；
6. 让 Qoder 可以依据本方案对当前仓库进行差异分析，并以最小改动更新协作规范。

本方案不是新的产品 PRD。产品需求仍以 `docs/PRD.md` 为准；本方案定义的是“如何开发、如何交接、如何确认、如何验收”。

## 2. 核心协作模型

### 2.1 总体分工

采用以下默认比例：

- **Qoder：约 75%**
- **Codex：约 25%**
- **用户：所有关键产品和架构决策的最终确认人**

### 2.2 Qoder 的默认职责

Qoder 是日常主开发工具，默认负责：

- 当前阶段任务规划；
- A/B/C 决策清单整理；
- 普通业务逻辑；
- React 组件、页面、样式和交互；
- 表单、列表、浮窗、状态展示；
- 常规 Contracts 和 API 接入；
- 常规 Python Sidecar 接口；
- 前后端联调；
- 受影响模块的最小测试；
- 更新任务文件和 `HANDOFF.md`；
- 阶段完成后的 Git 收尾。

### 2.3 Codex 的默认职责

Codex 只在以下高价值场景介入：

- 核心架构和跨层接口设计；
- Agent、Skill、Orchestrator、Model Router；
- 数据库迁移、数据恢复和复杂状态一致性；
- API Key、安全凭据、系统权限和敏感信息；
- 串口、固件、Shell、文件沙箱和回滚；
- Code Agent 的 Patch、快照、测试执行和修复循环；
- CadQuery 等本地执行框架；
- 三个以上核心模块的跨层重构；
- Qoder 连续两轮仍无法修复的问题；
- MVP 集成、Windows 打包、发布前验收。

### 2.4 用户的职责

用户负责：

- 确认所有 A 类决策；
- 确认是否接受 B 类默认值；
- 决定是否调用 Codex；
- 实际操作桌面应用进行手工验收；
- 确认阶段是否可以提交和关闭；
- 决定是否进入下一阶段。

## 3. 掌问不可违反的产品约束

以下规则是所有阶段、所有工具都必须遵守的长期约束。

### 3.1 界面约束

1. 中央区域始终属于 `MainConversation`；
2. 未选择项目时，中央区域只能显示主对话内部的简洁引导状态；
3. 新建项目、项目列表和项目管理必须位于左侧栏，或者由左侧入口触发浮窗；
4. 不允许在中央区域放置完整的新建项目表单；
5. 右侧一级栏目固定为：
   - 工作；
   - 产物；
   - 设备；
6. 文档、代码、3D 模型、设置和完整设备控制台通过右侧栏或浮窗查看；
7. 打开或关闭浮窗不得卸载主对话，不得丢失草稿；
8. UI 尽可能简洁，不设计成复杂 IDE；
9. 普通用户模式隐藏 Agent、Skill、模型参数和底层工具细节；
10. 所有状态必须提供中文文字，不能仅依赖颜色。

### 3.2 产品流程约束

1. 前台同时只展示一套当前推荐实现方案；
2. 推荐内容必须是完整实现方案，不能只包含硬件；
3. 用户通过对话不断修改当前方案，直到确认；
4. 立项书只能基于已确认的实现方案生成；
5. Orchestrator 根据已批准立项书选择所需 Agent；
6. Agent、Skill、模型、Provider 和 Tool Runner 必须解耦；
7. 同一 Agent 可按步骤使用不同模型；
8. 多个 Agent 可以共享同一模型；
9. MicroPython 日常代码上传默认使用 USB 串口；
10. 所有高风险本地操作必须保留人工确认点。

### 3.3 安全约束

1. 云端 LLM 不得直接操作 Shell、串口和本地文件系统；
2. 本地操作必须经过 Tauri/Sidecar/Tool Runner 权限边界；
3. API Key 不得进入普通 JSON、项目数据库、日志、console、测试快照和 Git；
4. API Key 与项目数据完全隔离；
5. 擦除 Flash、烧录固件、覆盖关键文件必须二次确认；
6. 发布和导出前必须扫描 API Key、Wi-Fi 密码和 Token；
7. 测试默认不得请求真实付费 LLM；
8. 不提交个人绝对路径、缓存、构建产物和本机环境文件。

## 4. 仓库中的协作文件体系

为减少每次提示词长度，固定规则必须写入仓库。

### 4.1 文件职责

| 文件 | 作用 | 更新频率 |
|---|---|---|
| `AGENTS.md` | 长期不变的产品、架构、安全和工具规则 | 很低 |
| `WORKFLOW.md` | 统一规划、确认、实施、验收和提交流程 | 低 |
| `CURRENT_TASK.md` | 当前阶段编号、目标、非范围、主工具 | 每阶段 |
| `HANDOFF.md` | 当前真实进度、测试结果、已知问题和下一步 | 每次交接 |
| `PLANS.md` | 阶段路线图与状态 | 每阶段 |
| `tasks/ZW-xxx-*.md` | 当前阶段详细任务、决策、里程碑和验收 | 每阶段 |
| `docs/PRD.md` | 产品需求基线 | 按产品变更 |
| `docs/ARCHITECTURE.md` | 架构基线 | 架构变更时 |
| `docs/UI_CONTRACT.md` | 界面不可违反的结构规则 | UI 基线变更时 |
| `docs/API_EVENTS.md` | 前后端接口和事件协议 | 接口变更时 |
| `docs/DECISIONS.md` | 长期架构决策记录 | 关键决策时 |

### 4.2 真相优先级

发现内容冲突时，按以下顺序判断：

1. 当前可验证代码和自动测试；
2. 当前任务文件中已确认的 Decision Log；
3. `docs/PRD.md` 和 `docs/UI_CONTRACT.md`；
4. `docs/ARCHITECTURE.md` 和 `docs/API_EVENTS.md`；
5. `HANDOFF.md`；
6. 工具聊天记录。

聊天记录不得作为唯一依据。

## 5. 每个阶段的标准生命周期

### 5.1 阶段准备

开始新阶段前：

1. 确认前一阶段已经手工验收；
2. 确认前一阶段已经提交并打标签；
3. 确认 `git status` 干净；
4. 更新 `CURRENT_TASK.md`；
5. 创建当前阶段任务文件草案；
6. 创建阶段分支。

推荐分支命名：

```text
feature/zw-004-clarification-solution
feature/zw-005-hardware-library
feature/zw-007-orchestrator
```

### 5.2 规划阶段

Qoder 读取：

- `AGENTS.md`
- `WORKFLOW.md`
- `CURRENT_TASK.md`
- `HANDOFF.md`
- 当前任务文件
- 最近两个 Git 提交
- 当前阶段直接涉及的代码

规划阶段只输出：

- 已有能力复用分析；
- 实施里程碑；
- 涉及文件；
- 最小测试；
- 明确非范围；
- A/B/C 类决策；
- 是否建议 Codex 介入。

规划阶段不得修改业务代码。

### 5.3 用户确认阶段

用户必须明确回复：

- 每个 A 类决策的选择；
- 是否接受 B 类默认值；
- C 类是否允许自行处理；
- 哪些事项交给 Codex；
- 是否允许新增主要依赖；
- 最终任务范围。

确认结果必须写入当前任务文件的 `Decision Log`。

### 5.4 实施阶段

Qoder 按已确认的里程碑实施：

- 只完成当前任务；
- 保留已有正确实现；
- 不因风格偏好重写；
- 每个里程碑运行相关最小测试；
- 发现需要改变 A 类决策时立即停止；
- 不自动提交；
- 不进入下一阶段。

### 5.5 Codex 介入阶段

只有满足介入条件时才使用 Codex。

Codex 只读取：

- `AGENTS.md`
- `WORKFLOW.md`
- `CURRENT_TASK.md`
- `HANDOFF.md`
- 当前任务文件中的“需要 Codex 介入”章节
- 最近两个 Git 提交
- 直接涉及的代码和测试

Codex 不重新规划完整阶段，不重做 UI，不重复验证未修改模块。

### 5.6 Qoder 联调阶段

Codex 完成核心部分后，Qoder：

- 读取最新交接；
- 使用 Codex 定义的 Contracts 和接口；
- 完成剩余 UI 和普通逻辑；
- 不改变核心安全边界；
- 运行受影响最小测试。

### 5.7 阶段验收

Qoder 进行阶段内验收：

- 不增加功能；
- 检查任务验收条件；
- 只运行受影响测试；
- 检查敏感信息和 Git 状态；
- 更新 `HANDOFF.md` 和任务文件；
- 输出“通过 / 附条件通过 / 不通过”。

### 5.8 用户手工验收

用户至少实际检查：

1. 桌面应用能否启动；
2. 核心操作流程是否可用；
3. UI 是否符合产品信息架构；
4. 中央主对话是否始终保留；
5. 浮窗和右侧栏是否影响草稿；
6. 错误提示是否可理解；
7. 重启后数据是否正确；
8. 是否出现后台进程残留；
9. 是否出现重复入口；
10. 是否有敏感信息泄露。

### 5.9 提交和关闭

手工验收通过后：

1. 检查 `git diff`；
2. 排除敏感信息和构建产物；
3. 更新任务和交接文件；
4. 显式暂存当前阶段文件；
5. 创建提交；
6. 创建阶段标签；
7. 更新 `PLANS.md`；
8. 不自动进入下一阶段。

推荐提交：

```text
feat: complete ZW-004 clarification solution
```

推荐标签：

```text
zw-004-complete
```

## 6. A/B/C 决策机制

### 6.1 A 类：必须确认

未得到用户明确确认前不得实施。

典型事项：

- 技术栈或主要依赖变化；
- 数据库存储和迁移方案；
- API Key 和系统权限；
- 用户主流程变化；
- 任务范围扩大或缩小；
- Agent 自动执行权限；
- 串口和固件高风险操作；
- 公开分享和数据上传云端；
- 与 PRD 不一致的方案。

每项 A 类决策必须包含：

- 编号；
- 当前问题；
- 方案一、方案二或更多；
- 优缺点；
- 当前影响；
- 后续影响；
- 推荐方案和理由；
- 用户应如何回复。

### 6.2 B 类：建议确认

有安全、可逆的推荐默认值。用户确认整体规划且未反对时，可以采用。

典型事项：

- 列表默认排序；
- 自动保存防抖时间；
- 文案；
- 默认分页数量；
- 非关键动画和视觉状态。

### 6.3 C 类：可自行决定

只能包含：

- 不改变产品需求；
- 不改变技术基线；
- 不影响数据兼容；
- 不增加权限；
- 可以轻易回滚的实现细节。

典型事项：

- 组件内部命名；
- 样式间距；
- 测试辅助函数；
- 私有方法拆分。

## 7. 最简日常指令

固定规则写入仓库后，日常只使用以下短指令。

### 7.1 规划当前任务

```text
读取 AGENTS.md、WORKFLOW.md、CURRENT_TASK.md 和 HANDOFF.md。
按照 WORKFLOW.md 规划当前任务，检查现有实现，避免重复开发。
只输出实施计划、最小测试和 A/B/C 类确认事项，不修改业务代码。
完成后停止等待我确认。
```

### 7.2 确认规划并实施

```text
规划整体确认。
A-01：选择……；A-02：选择……。
B类接受推荐默认值，C类允许自行处理。
请把决策写入当前任务文件的 Decision Log，并按照 WORKFLOW.md 实施当前任务。
不要提交，不进入下一阶段。
```

### 7.3 手工验收发现问题

```text
当前任务手工验收发现问题：
1. 问题：……
2. 重现步骤：……
3. 预期行为：……
4. 实际行为：……
只修复上述问题，不扩大范围，不重构已通过功能。
修复后运行相关最小测试，并给出复测步骤。
```

### 7.4 验收当前任务

```text
按照 WORKFLOW.md 验收当前任务。
只检查当前任务验收条件和受影响模块，不重复验证历史阶段，不增加功能。
更新 HANDOFF.md 和当前任务文件，输出验收结论。
不要提交，不进入下一阶段。
```

### 7.5 提交当前阶段

```text
当前任务手工验收通过。
按照 WORKFLOW.md 完成 Git 收尾：检查敏感信息和构建产物，更新 HANDOFF 和任务文件，提交当前阶段并创建完成标签。
完成后停止，不进入下一阶段。
```

### 7.6 Codex 介入

```text
读取 AGENTS.md、WORKFLOW.md、CURRENT_TASK.md、HANDOFF.md 和当前任务文件。
只处理“需要 Codex 介入”章节中的事项。
不要重新规划完整阶段，不修改普通 UI，不重复验证未修改模块。
完成后更新 HANDOFF.md 中的 Codex 交接说明，并停止。
```

### 7.7 Codex 完成后交回 Qoder

```text
读取 HANDOFF.md 中最新的 Codex 交接结果。
继续完成 CURRENT_TASK.md 中的剩余工作。
不要修改 Codex 确定的核心接口和安全边界，不重复已通过测试。
```

## 8. 最小测试策略

### 8.1 日常原则

按修改影响范围选择测试，不进行无意义全量回归。

| 修改范围 | 最小测试 |
|---|---|
| 只改 UI 样式 | 前端类型检查 + 对应组件测试 |
| 改 React 状态 | 前端类型检查 + 行为测试 |
| 改 Contracts | Contracts 构建/类型检查 + 受影响前端类型检查 |
| 改 Sidecar | 对应 Python 测试 |
| 改 LLM Provider | Provider Mock + 错误映射测试 |
| 改数据库 | 仓库测试 + 迁移/恢复测试 |
| 改 Tauri | `cargo check` + 桌面启动 |
| 改启动脚本 | 实际启动与退出一次 |
| 改串口 | Mock 设备测试 + 人工设备验证 |
| 多模块变更 | 当前阶段完整验证 |

### 8.2 全量回归节点

建议仅在以下节点执行全量回归：

- ZW-006 完成后；
- ZW-009 完成后；
- ZW-012 完成后；
- ZW-015 完成后；
- ZW-016 MVP 验收；
- ZW-017 发布构建。

### 8.3 必须完整验证的阶段

- ZW-012：串口和固件；
- ZW-016：MVP 端到端；
- ZW-017：安装和发布。

## 9. Git 与文件卫生规则

### 9.1 不应进入 Git

- `.venv/`
- `node_modules/`
- `dist/`
- `target/`
- `.data/`
- 日志
- 缓存
- API Key
- Token
- Wi-Fi 密码
- 本机绝对路径
- 临时导出包
- `.qoder/repowiki/`，除非项目明确决定纳入

### 9.2 提交规则

- 不盲目使用 `git add -A`；
- 先检查 `git status` 和 `git diff`；
- 显式暂存当前阶段文件；
- 一个提交只表达一个清晰目的；
- 文档与功能保持同步；
- 阶段标签指向阶段最终提交。

### 9.3 工具切换规则

Qoder 交给 Codex 前：

- 先提交或建立明确 checkpoint；
- 更新 `HANDOFF.md`；
- 列出需要 Codex 介入的具体事项；
- 不让 Codex 猜测当前进度。

Codex 交回 Qoder 后：

- 写明新增接口；
- 写明安全边界；
- 写明已运行测试；
- 写明剩余工作；
- Qoder 不得擅自改变核心接口。

## 10. 后续阶段分工路线

### 10.1 ZW-003：项目与会话持久化

**状态建议：** 已完成，进行 UI 收尾和阶段关闭。  
**Qoder：** 修复剩余 UI、验收、提交。  
**Codex：** 不再参与，除非出现数据库或持久化严重问题。

### 10.2 ZW-004：需求澄清与唯一实现方案

**Qoder 主负责：**

- 澄清状态和卡片；
- DeepSeek 结构化调用；
- 需求完整度；
- 当前唯一方案；
- 方案浮窗；
- 版本和确认；
- 普通测试。

**Codex 介入条件：**

- 结构化输出长期不稳定；
- 状态机无法恢复；
- 方案版本关系发生跨模块错误。

**用户必须确认：**

- 每轮最多问题数量；
- 完整度阈值；
- 是否允许跳过；
- 确认后如何修改；
- 修改是否生成新版本。

### 10.3 ZW-005：硬件库与规则引擎

**Qoder：** CRUD、硬件库 UI、库存、搜索、普通接口。

## 11. 推荐的 `WORKFLOW.md` 标准内容

仓库应存在一份简洁、可执行的 `WORKFLOW.md`。推荐正文如下：

```markdown
# 掌问开发工作流

## 1. 开始任务

读取 AGENTS.md、CURRENT_TASK.md、HANDOFF.md、当前任务文件、最近两个 Git 提交和当前任务涉及的代码。不要重新盘点整个仓库。

## 2. 规划

用户说“规划当前任务”时：

1. 只分析，不修改业务代码；
2. 检查已有实现，避免重复开发；
3. 输出里程碑、文件、最小测试和明确非范围；
4. 输出 A/B/C 类决策；
5. 标记是否需要 Codex 介入；
6. 完成后停止。

## 3. 确认

A 类必须由用户明确确认。B 类可采用推荐默认值。C 类可自行处理。确认结果写入当前任务的 Decision Log。

## 4. 实施

1. 只完成当前任务；
2. 保留已有正确实现；
3. 不进行无关重构；
4. 每个里程碑运行相关最小测试；
5. 需要改变 A 类决策时停止；
6. 不自动提交；
7. 不进入下一阶段。

## 5. Codex 介入

仅用于核心架构、数据迁移、安全凭据、串口固件、Agent 调度、文件沙箱、复杂跨模块问题和发布构建。普通 UI 与常规逻辑由 Qoder 完成。

## 6. 验收

用户说“验收当前任务”时：

1. 不增加功能；
2. 检查任务验收条件；
3. 只运行受影响测试；
4. 检查敏感信息和 Git 状态；
5. 更新 HANDOFF.md 和任务文件；
6. 输出通过、附条件通过或不通过；
7. 不自动提交。

## 7. 收尾

用户确认手工验收通过后：

1. 检查 Git diff；
2. 排除敏感信息、缓存和构建产物；
3. 更新 HANDOFF.md 和任务文件；
4. 显式暂存当前阶段文件；
5. 提交并打阶段标签；
6. 不进入下一阶段。
```
