# MicroPython 工程闭环

## 正式工程 Spec 门禁

- 已确认立项书代表进入正式工程流程：先从该立项版本生成工程 Spec，完成硬件 Skill、BOM、IO Map 和规则校验，再等待用户确认。
- 当前 Spec 未生成、未通过校验、被退回或未确认时，不得生成正式工程代码草稿，也不得用聊天代码绕过门禁。
- Spec 确认后，代码必须绑定该 Spec 版本，依次通过结构化输出校验、文件/依赖/Board API 门禁和本地静态与语法检查，最后作为完整代码版本打开编辑器。
- 没有进入立项流程的简单、临时代码问答仍可直接给出受限草稿，但不能伪装成已完成的正式工程交付。

## 开发板优先

1. 从项目事实、确认方案、IO Map 和用户消息确定目标板。
2. 读取匹配的 Markdown BoardProfile；找不到时先询问准确板型，不套用通用 ESP32 引脚。
3. 核对板载资源、扩展口、电压、电流、驱动、固件和 MicroPython 专用模块。
4. 检测冲突后说明影响并请求确认；不能静默改动用户已确认的端口或器件。

## 代码结构

- 默认只生成设备会实际运行并上传的 `src/main.py`，尽可能把完整程序收束在一个文件中。
- 只有单文件会明显损害可读性或确实需要复用模块时，才增加平级 `src/*.py`；`main.py` 必须显式导入所需模块，产物、验证和上传必须包含完整文件集。
- 多文件时可把阈值、引脚和非敏感运行参数放入 `src/config.py`；凭据只保留占位符，不生成不会上传的 README、测试或驱动占位文件。
- 对水泵、电机和加热器增加最大连续工作时间、冷却或锁止策略和默认安全状态。
- 代码使用目标板官方 MicroPython API，不混入 Arduino、CPython 或其他开发板专用库。

## 用户修改

- `currentCode.modifiedByUser=true` 时，先承认用户保存的版本和变更摘要。
- 以 `currentCode.files` 为当前事实，不能引用旧模型草稿覆盖用户修改。
- `requiresValidation=true` 时明确说明尚未验证，并根据改动范围建议静态检查、Mock 或设备验证。
- 读取 `currentCode.testResult.checks` 的真实退出码和状态；已运行但失败时说明具体失败项，不能因 `requiresValidation=false` 声称验证通过。
- 用户要求继续修改时基于当前版本增量更新，保留旧版本用于比较和恢复。

## 验证和上传

1. 语法、导入、BoardProfile、IO 和安全规则检查。
2. 使用无真实 GPIO/网络副作用的 Mock 测试验证纯逻辑。
3. 代码编辑器底部使用“验证并接受代码”完成静态、语法检查和接受；失败时保持未接受并显示真实命令、退出码和输出，不再回到中央对话二次接受。
4. 用户确认后才允许本地 Tool Runner 通过 USB 串口上传文件。
5. 上传与固件烧录分离。普通代码变更不擦除 Flash、不重刷 MicroPython。
6. 真实上传需要备份、端口锁、超时、取消、幂等标识，并记录重连、启动日志和核心功能证据。

执行状态只相信本地工具的退出码和结构化结果。失败不能显示为通过，未运行不能显示为已验证。
